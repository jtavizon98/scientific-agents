# Delegation

Dispatch only after defining the deliverable, evidence sources, owner, safe
write boundary, forbidden actions, verification, and stopping conditions. When
the task includes a consequential action, record the authorization source,
scope, target, and time rather than relying on task ownership alone.

For remote work that may outlive one interactive step, also apply the
long-job procedure. Delegating polling does not transfer the parent objective
or permit the parent to stop before downstream validation, report, review, and
requested notification gates are complete.

## Choosing a role

| Need | Preferred choice | Constraint |
| --- | --- | --- |
| Inspect-only planning or audit | A plan or read-only mode of the client | Leave plan mode and update scope before writes |
| Interactive implementation loop | The client you are already using | Choose deliberately; preserve one writer |
| Phone or remote control | A client with a verified remote-control feature | Verify session and runtime identity before steering |
| Autonomous evidence-heavy work | A client with verified boundary, review and continuation support | Verify those properties in the active client |
| Bounded mechanical edits | A cheap suitable model | Precise scope and review required |
| Numerical or scientific judgment | A separate session of a strong model, preferably from a different family than the author, including for the final pass | Human domain review still required |

Select model and effort explicitly where the client supports it rather than
inheriting the primary model by accident. Appearance-only review defaults to an
economy image-capable route, independently of the author's model. Name the
route, the effort (or that it is not visible), the selected pages, the
remaining reading task and the stopping condition before launch. Escalate to an
expensive model only for a named unresolved capability or finding, not because
it is the final review or the document contains physics. A quota failure
changes availability, not the required capability. Retain completed evidence
rather than restarting the audit. If your render gate has a preflight, run it
on the exact gate and request first; it is an executable check, not a universal
interception hook, so do not claim harness enforcement that is absent.

Do not delegate ambiguous ownership, credential access, destructive cleanup,
job control, or final scientific conclusions to a mechanical worker.

## Dispatch packet

Use the [BRIEF template](templates/BRIEF.md). Give one owner a branch and
worktree by default. Preserve source commitments: distinguish requirements,
evidence, assumptions, and proposals. Require the worker to keep `STATE.md`
current and leave a `RESULT.md` even when blocked.

In every cross-host packet distinguish the control client, the agent runtime and
writing host, the worktree owner, and the execution host chosen for the work.

A monitor packet must be bounded by exact job identifiers, one status surface,
a polling deadline, allowed validation, forbidden job actions, and a handback
condition. The parent remains responsible for consuming the evidence and
finishing the durable completion contract.

## Review

Review diffs and evidence, not confidence. A review finding stands when a run
or calculation shows it, or when it names an exact missing assumption or
contradiction with a cited line. Keep speculative risks in a separate list;
they do not block acceptance on their own. A vision worker may report layout,
labels, clipping, or visual anomalies; these are observations until compared
with source data and intended rendering. Re-run proportionate checks in the
owning environment before accepting consequential conclusions. Before accepting
a handback, reconcile the complete parent contract, including the final
reviewable artifact, human-review state, Git handoff, delivery, blocker
escalation, and completion notification. A worker finishing its bounded step
does not close those gates.
