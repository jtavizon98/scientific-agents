\section{Choose the result before the client}

\begin{headline}
  Name what should be different when the work is done. That decides the owning
  repository, the evidence, and whether the work needs a short interactive exchange or a
  durable session.
\end{headline}

``Explain where these two cutflows first diverge'' asks for an investigation. ``Change the
selection and show its effect'' adds implementation and scientific validation. Before
acting, identify the owning repository or document, the evidence available and the result
the reader will inspect \cite[rules 1--3]{skill:coordination}.

\paragraph{Write a concrete completion sentence.} For a substantial task, name an
assessable intermediate outcome: ``The comparison report is ready for my review when the
inputs and cutflows have been checked, the report passes internal reviews, and the exact
PDF is available locally.'' Human acceptance stays open. A code-only task names its
implementation, checks and reading guide instead; it needs a report only when its contract
asks for one \cites[rule 4]{skill:coordination}[Verify and hand back]{skill:coding}.

\paragraph{Coming back to work.}
\begin{itemize}
  \item \textbf{You did not follow it:} ask for \code{ketchup}. It says in plain words what
        changed since your last message, keeps the result numbers with what they measure,
        and lists each decision waiting on you with the agent's pick, evidence and risk
        \cite{skill:ketchup}.
  \item \textbf{You need to understand code or a method:} ask the agent to \code{teach} it:
        a plain definition first, then the mechanism one piece at a time
        \cite{skill:teach}.
\end{itemize}

\section{Identify the owner and the execution boundary}

\begin{headline}
  Control, source ownership and execution are separate roles. Know which machine holds
  each before you edit.
\end{headline}

A phone can steer an agent on a workstation whose worktree holds the source while an
authorized job runs on a third host (Figure~\ref{fig:roles}). The phone's location moves
neither the source nor the job's owner \cite[GUI, terminal and cross-client
  sessions]{skill:workflow-gui}.

\begin{figure}[H]
  \centering
  \begin{tikzpicture}[node distance=10mm]
    \node[open,text width=110mm] (ui) {\textbf{Control surface}\\phone or laptop;
      choose the intended session};
    \node[work,text width=110mm,below=of ui] (runtime) {\textbf{Agent runtime and owned worktree}\\
      observed host, repository, branch, writing owner};
    \node[work,text width=110mm,below=of runtime] (run) {\textbf{Execution target, when needed}\\
      capable environment and explicitly authorized job};
    \draw[flow] (ui)--node[right,font=\footnotesize]{steer}(runtime);
    \draw[flow] (runtime)--node[right,font=\footnotesize]{run / inspect}(run);
  \end{tikzpicture}
  \caption{Control, source ownership, and execution are separate roles. This is a
    routing model, not evidence of a particular live connection.}
  \label{fig:roles}
\end{figure}

Before editing, inspect:
\begin{enumerate}
  \item the literal host and the active session;
  \item Git state and the worktree;
  \item whether report or software edits would overlap another task on the same machine; if so,
        use an isolated worktree \cite[Start a writing task; Commit and hand off]{skill:git}.
\end{enumerate}

\begin{rulebox}[Unfamiliar changes]
  An unfamiliar dirty path needs ownership evidence. Preserve it while you resolve who owns
  it; never reset it to make the checkout look convenient.
\end{rulebox}

\section{Keep the work loop small and the ending explicit}

\begin{headline}
  Alternate one coherent change with the evidence that assesses it, and close only the
  gates the task names.
\end{headline}

Remote execution belongs inside the loop whenever a check needs remote data or software
(Figure~\ref{fig:loop}). Not every task ends in a report, and not all validation comes
before execution.
